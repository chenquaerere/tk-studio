## 一、为什么这样合并（两程序体检结论）

| 维度 | ① TK 作品链接采集器 | ② TK 去水印高清程序 |
|---|---|---|
| 原路径 | `D:\workbuddy\TK链接抓取助手`（源码 `D:\TikTokLinkCollector`） | `D:\tiktok去水印\TK去水印高清程序_v4.0.0` |
| 版本 | v1.2.1 | v4.0.4 |
| Python | 3.10.11 | 3.10.11 |
| UI 范式 | customtkinter **原生窗口**（8 个页面） | FastAPI + **WebView2 网页界面**（SSE 推送） |
| 业务后端 | Playwright 无头浏览器采集 + SQLite | TikWM/抖音解析 + PyTorch 超分 |
| 打包形态 | PyInstaller onedir | C# 托盘启动器 + 嵌入式 Python（文件夹即程序） |
| 体积 | 部署目录 2.0G（浏览器内核 1.39G 在 `%LOCALAPPDATA%`） | 7.6G（torch 独占 4.2G） |

**三条决定性结论**

1. **UI 范式完全不同** ⇒ 不可能"简单拼接"，只能二选一：把采集器搬进 Web 外壳，或把去水印搬进 Tk 外壳。**选定前者**：采集器的 8 个页面都是表格/表单型，迁到 Web 反而更清晰；去水印那套 Web 界面零损失保留。
2. **Python 版本一致（3.10.11）** ⇒ 依赖无硬冲突，只缺 playwright / customtkinter / openpyxl。
3. **体积由 torch 决定** ⇒ PyInstaller 打不动 4G 级依赖，必须沿用"文件夹即程序"形态。

```

│   │   ├─ config.py                  ★ 统一配置 + 旧配置自动迁移
│   │   ├─ version.py                 ★ 品牌 / 版本唯一来源
│   │   └─ errors.py                  类型化错误体系
│   ├─ collector\                     采集内核（移植自 A，UI 无关化）★W2
│   ├─ watermark\                     去水印 + 高清内核
│   │   ├─ core\                      引擎 / 配置 / 输出 / 预设
│   │   └─ tiktok\                    解析 / 下载 / 历史 / 反爬签名
│   ├─ server\                        FastAPI 服务层 + SSE
│   ├─ ui\                            事件总线（与界面无关）
│   ├─ frontend\                      统一 Web UI（HTML/CSS/JS）★W4
│   └─ assets\icon.ico                ★ 图标取自采集器（md5 cde614e0…）
├─ runtime-py → python-runtime\       Python 3.10.11 嵌入式运行时
├─ venv\                              统一依赖环境（torch + playwright…）
├─ models\  tools\ffmpeg\  gfpgan\    超分模型 / 转码器 / 人脸修复
├─ data\                              ★ 用户数据（数据库 21 账号 / 84 作品 + 登录态）
├─ runtime\ logs\ exports\ backups\ links_log\
├─ docs\  scripts\  release\
└─ CHANGELOG.md  README.md
```

**分层职责**（依赖只能单向向下，禁止反向依赖）：

```
frontend (Web UI)
      ↓ HTTP / SSE
server (FastAPI 路由 + 任务编排 + 事件总线)
      ↓
collector (采集内核)      watermark (去水印 + 高清内核)
      ↓                          ↓
common (paths / config / version / errors)
      ↓
底层引擎：Playwright · TikWM/yt-dlp · PyTorch/Real-ESRGAN · ffmpeg
```

## 三、UI 架构方案

### 3.1 导航结构（4 组 16 视图）

按**工作流**分组，用户无需知道功能来自哪个旧程序。

| 分组 | 视图 | 来源 | 说明 |
|---|---|---|---|
| **总览** | 仪表盘 | A | 账号/作品/任务/聊天采集只读统计、未完成任务横幅、最近任务 |
| **采集工作流** | 账号管理 | A | 昵称·账号·地区·采集数量；状态筛选、全选反选、批量启停、文件导入 |
| | 聊天链接采集 | A | 好友/群聊视频链接采集；登录、最近使用、导出、清空单目标 |
| | 采集任务 | A | 按地区选号 + 逐账号数量，串行采集；暂停/继续、失败重试、恢复未完成 |
| | 采集结果 | A | 默认只显示**本次采集**，含采集时间列；日期/状态/关键词筛选、分组导出 |
| | 每日归档 | A | 按日期看已采到的链接（`links_log/YYYYMMDD.txt`） |
| | 历史记录 | A | 任务级台账 + 详情（账号明细 / 全部链接 / 复制 / 导出） |
| **素材制作** | 去水印 | B | 粘贴链接 → 解析 → 批量下载；可自选保存目录 |
| | 高清修复 | B | Real-ESRGAN 超分 + GFPGAN 人脸修复；可自选保存目录 |
| | 素材库 | B | 历史下载与输出浏览 |
| | 模型中心 | B | 模型清单 / 显存占用 / 下载 |
| **系统** | 任务中心 | A+B | 进程内任务（采集/下载/超分）的进度与日志，SSE 实时 |
| | 工具箱 | B | 转码、ZIP 打包、重命名等 |
| | 运行日志 | A | 程序日志尾部读取 + 级别筛选着色 + 打开日志目录 |

**交互约定**（沿用采集器已验证的教训）
- 关键操作**不依赖模态确认框**（易被遮挡 + `grab_set` 吞事件），改按钮内联二次确认。
- 列表**整行可点**，不只点控件本身。
- 跨线程更新统一走主线程调度，禁止子线程直接操作界面。
- 空态、加载态、错误态三态必须齐全；清空时要连表格与附属面板一起清。
- 长任务一律显示阶段文案 + 进度 + ETA，否则用户判定为"点了没反应"。

## 四、配色方案

**风格方向：深空科技感（Dark Tech）** —— 深色底 + 电光紫主色 + 青绿强调，克制的高级感，适配"专业素材工具"定位。

主色取自采集器（保留其已被验证的深色设计基因），强调色取自去水印（TikTok 品牌青），
相当于把两条产品线的视觉基因各留一半。

### 4.1 中性色

| Token | 色值 | 用途 |
|---|---|---|
| `--bg` | `#0E1116` | 窗口底板 |
| `--sidebar` | `#131722` | 左侧导航栏 |
| `--surface` | `#171C28` | 卡片 / 表格容器 |
| `--surface-2` | `#1E2534` | 行悬停 / 次级表面 |
| `--border` | `#262E3E` | 分隔线 / 描边 |

### 4.2 品牌与语义色

| Token | 色值 | 用途 |
|---|---|---|
| `--primary` | `#6C63FF` | 主按钮、激活态、选中 |
| `--primary-hover` | `#5A52E0` | 主色悬停 |
| `--primary-soft` | `#242B52` | 选中底 / 徽章底 |
| `--accent` | `#25F4EE` | 链接、进度、高亮数值 |
| `--accent-soft` | `#103B3E` | 强调柔底 |
| `--brand` | `#FE2C55` | 「去水印」板块标识 / LOGO |
| `--success` | `#22C55E` | 完成、最近采集时间 |
| `--warning` | `#F59E0B` | 重试、待处理 |
| `--danger` | `#EF4444` | 删除、失败 |

### 4.3 文字色（三级）

| Token | 色值 | 用途 |
|---|---|---|
| `--text` | `#E6E9F0` | 主文字、标题、数值 |
| `--text-2` | `#9AA3B8` | 次级文字、副标题、表头 |
| `--text-3` | `#6B7488` | 弱文字、提示、占位 |

对比度：`--text` 对 `--surface` 约 13:1，`--text-2` 约 6.2:1，`--text-3` 约 3.6:1
（前两者远超 WCAG AA 4.5:1；`--text-3` 仅用于非关键提示信息）。

### 4.4 字体 / 圆角 / 间距

- 中文：`"Microsoft YaHei UI", "Segoe UI", system-ui`
- 数字与 ID：`Consolas, ui-monospace`（等宽，便于核对 19 位作品 ID）
- 字号阶梯：11 / 12 / 13 / 14 / 16 / 18 / 22 / 28
- 圆角：`8px`（控件）/ `12px`（卡片）/ `14px`（容器）/ `999px`（胶囊）
- 间距：4 / 8 / 12 / 16 / 20 / 24 / 32

### W5-E 随身浏览器内核（零依赖便携的关键一步）

采集依赖 Playwright，而 Playwright 默认从 `%LOCALAPPDATA%\ms-playwright`
取浏览器内核 —— **换台电脑、换个用户账户就失效**。
`collector/bootstrap.py::_use_bundled_browsers()` 在导入 playwright **之前**
把 `PLAYWRIGHT_BROWSERS_PATH` 指向程序目录内的 `runtime/ms-playwright/`。

`scripts/verify_bundled_browser.py` → **4/4 PASS**：

| 项 | 内容 | 结果 |
|---|---|---|
| T0 | 内核目录就位（317 文件 / 437 MB） | ✅ |
| T1 | `chromium.executable_path` 落在 `runtime/ms-playwright/chromium-1243/`（而非系统缓存） | ✅ |
| T2 | 真实启动并渲染页面（Chromium 153.0.8010.12），截图存档 | ✅ |
| T3 | **模拟干净机器**：把 `LOCALAPPDATA` 指向空目录（= 这台机器从没装过 Playwright），仍成功启动，且未回写假缓存 | ✅ |

T3 才是「换台电脑直接双击就能用」的等价证明。

**体积决策**：内核完整复制是 707 MB（`chromium-1243` 433M + `chromium_headless_shell-1243` 271M
+ ffmpeg/winldd 4M）。但采集侧**恒用完整 Chromium**（`browser.py` 固定
`headless=False` + 注入 `--headless=new`，刻意避开指纹明显的 headless-shell），
headless-shell 属死重量。实测把它移走后 4/4 仍通过，因此**不纳入分发**
（`chrome-headless-shell` 是系统的一份，需要时可随时拷回），内核降到 **437 MB**。

**防漂移断言**：Playwright 靠目录名 `chromium-<revision>` 找内核，升级 playwright 包后
revision 会变，报错却是 `Executable doesn't exist ... run playwright install`，
极易误判成路径配置问题。`verify_release.py` 因此新增
「随身内核版本与 Playwright 对齐」与「内核体积合理（< 600 MB）」两项断言。

**打包闸门**：`package.py` 增加 `--dry-run`（只列清单 + 根目录文件清单）与硬断言 ——
① 用户数据（`data`/`downloads`/`backups`/`exports`/`links_log`）**零文件混入**，
否则中止并列出泄漏样例；② 随身内核必须在清单里，否则中止（便携性会静默失效）。

**闸门当场抓到两处真实泄漏**（都不是 `data/` 这种显眼目录，而是散落的配置残留）：

| 泄漏项 | 问题 | 处置 |
|---|---|---|
| `config.legacy-20261008-150706.json` | W1 配置迁移的旧配置备份。`SKIP_FILES` 里写的是精确名 `config.legacy`，**匹配不到带时间戳后缀的实际文件名** | 改为**前缀匹配** `SKIP_FILE_PREFIX`，并同步排除 `_legacy*` |
| `docs/_legacy_watermark_config.json` | 含用户绝对路径（`C:\Users\<用户名>\Desktop\素材\高清后`） | 两个 `_legacy_*` 快照迁到 `backups/_legacy_config/`（该目录本就不进包） |

教训：**「排除用户数据」不能只盯大目录**，配置迁移留下的
`*.legacy*` / `_legacy_*` 快照同样会把个人路径带出去，且因为藏在 `docs/` 里更不容易被发现。

## 六、关键技术陷阱（已记录，后续 Wave 必须遵守）

1. **★ torchvision 兼容 shim**：`basicsr 1.4.2` 导入
   `torchvision.transforms.functional_tensor`，该模块在 torchvision ≥0.18 已移除。
   必须由 `watermark/core/engines/image.py:_patch_torchvision_compat()` 在导入前注入替身，
   否则 realesrgan / gfpgan / basicsr 全部 ImportError。
2. **★ 数据库永不递增 SCHEMA_VERSION**：`Database._migrate()` 在版本不一致时会
   DROP 全部业务表 —— 加字段只能走 `_EXTRA_COLUMNS` + `ALTER TABLE ADD COLUMN`。
   部署前必须在副本上验证用户真实库。
3. **★ 路径禁止按 `__file__` 数层数**：模块层级变动会让 `parent.parent` 静默指错目录
   （本次已在 6 处复现）。一律从 `common.paths` 取。
4. **★ 采集正确性五条铁律**（W2 移植时必须逐条保留）：
   不做跨运行去重、监听必须早于导航、置顶识别 `isPinnedItem`（今天/昨天的置顶额外采集）、
   `engine` 与 `collect_logic` 两套实现必须同步改、名额计数只统计非置顶。
5. **robocopy 退出码 1 表示成功**（有文件被复制），不是失败。
6. **去水印的下载模块状态仍在 `%APPDATA%\TikTokNoWatermark\`**
   （`config.json` / `history.json`），W3 已迁移进 `data/download/` 并**自动搬迁旧文件**
   （`watermark/tiktok/config.py:_migrate_legacy`），用户既有下载历史不丢。
7. **★ 长任务 API 必须有显式范围闸门**：采集是"替换式记录"（先删所选账号既有作品再采），
   任何"空参数 → 隐式全量"的兜底都可能清空用户数据。见 `docs/INCIDENT-20261008.md`。
8. **★ Playwright 浏览器内核必须随程序走**：默认从 `%LOCALAPPDATA%\ms-playwright`
   加载，换台电脑（或换用户账户）即失效。`collector/bootstrap.py:_use_bundled_browsers()`
   **在导入 playwright 之前**把 `PLAYWRIGHT_BROWSERS_PATH` 指向程序目录内的
   `runtime/ms-playwright/`。
   三个后续注意点：
   - 环境变量只在**尚未设置**时才写入，方便开发机临时指向别处；
   - Playwright 靠**目录名** `chromium-<revision>` 找内核，升级 playwright 包后
     revision 会变 → 报错却是 `Executable doesn't exist ... run playwright install`，
     极易误判成路径问题。已加断言（`verify_release.py`）盯住这个对齐关系；
   - 采集侧恒用完整 Chromium（`browser.py` 固定 `headless=False` + 注入
     `--headless=new`，避开 headless-shell 的指纹特征），因此
     `chromium_headless_shell-*`（271 MB）**不进分发**。
9. **验收脚本禁止调用会落库的端点**：采集是替换式记录，任何"顺手点一下"
   都可能清空用户数据。浏览器交互验证只在内存态操作（勾选 / 切视图 / 展开内联确认）。
10. **去水印与采集的 `session` 目录共用 `<程序根>/data/sessions`**，
   迁移登录态时直接复制 `data/` 即可复用，无需重新登录 21 个账号。
11. **★ 重写界面 ≠ 逐页对齐原界面**（W6 补记，本次功能大范围缺失的根因）：
    合并期间只把**采集内核**搬了过来，前端是照新接口**重新设计**的。
    结果是「旧程序有、而新接口没覆盖」的交互**静默消失**，且因为不报错，
    连验证脚本也查不出来 —— 一路带到发布后才被用户发现。
    **纪律**：迁移任何带 UI 的子系统时，必须拿原界面的**页面/控件清单**逐项打勾
    （而不是拿新 API 的路由清单反推界面），并保留一份「原版功能对照表」作为验收项。
12. **★「页面」对齐了不等于「控件」对齐了**（W7 补记，对 11 的加强）：
    W6 是拿原程序的**页面**打勾的，粒度只到页。复核后仍漏了 5 项，全部是
    **同一页面内、但后端接口没有对应端点**的控件 —— 账号页「编辑数量」、
    仪表盘「3 秒自动刷新」、设置页「恢复默认」与可编辑目录/更新源、
    聊天「停止」。判据很简单：**只要一个旧界面的控件找不到对应的后端能力，
    就一定是被漏掉的**（前端不可能凭空空转）。
    **纪律**：对照表的粒度必须细到控件，且要反向检查「原界面的每个按钮/输入框，
    在合并版里有没有落点」；缺后端就补端点，不要因为「接口没有」就删掉控件。
14. **★ 用机器比对代替人眼比对，并且**必须连布局一起比****（W8 补记，对 12 的加强）：
    12 的对照方式仍然是**人眼翻代码**，而且只比「控件在不在」，**没比布局**。
    结果用户看到的是「控件都在、但布局完全不一样了」——
    聊天页把「左列会话列表占主高度 + 右列操作区」的**两栏信息结构**
    改成了纵向卡片流，控件一个没少，可用性却全变了。
    **纪律**：① 差异比对写成**脚本**（`scripts/audit_ui_parity.py`：AST 抽文案 →
    归一化 → 全量查找 → 输出缺失清单与命中率），别靠记忆；
    ② 判据要覆盖**结构维度**（几栏、谁占主高度、区块顺序），不只是文案；
    ③ 少数由等价交互承载的差异（tkinter 模态框 / 独立窗口）必须在脚本里
    **逐条注明对应形态**，不允许为了刷绿随便加白名单。
13. **`alwaysReload` 视图里不要直接 `setInterval`**：每次进入该视图都会重新执行
    注册的回调，直接建定时器会**成倍泄漏**。正确做法是**单例定时器 + 守卫**
    （见 `collector.js::startDashboardAutoRefresh`：`document.visibilityState`、
    `location.hash`、有无 `.modal-mask` 三重判断）。
    本次已按此补回 21 项能力 + 3 个整页视图，对照结果记录在 §5 W6。
12. **★ 统计/只读端点里不许"顺手修"**：仪表盘一类聚合接口只做 COUNT / SELECT。
    在统计路径里补列、迁移或改设置，等于让"看一眼数据"变成一次写操作 ——
    在用户真实库上这是最不该有的风险。
13. **★ 验收脚本自身的"假失败"要当 bug 修**：W6 修掉三处（见 §5 W6）——
    依赖已被清理的历史文件、拿冻结快照的行数当断言、把"程序已在运行"判成失败。
    假的失败会训练人忽略红灯；假的通过比失败更危险。
15. **★ `alwaysReload` 的视图里，绑定函数必须幂等**（W9 补记）：
    `alwaysReload(pageId, fn)` 的实现是「跑完 `fn` 就把 `pageLoaded[pageId]`
    复位」，所以 **`fn` 每次进入该视图都会完整执行一遍**。
    如果 `fn` 里带了 `bindXxxOnce()`，而绑定函数每次都会 `addEventListener`，
    监听器就会层层叠加 —— 表现为「按钮点一下执行两次」「下拉菜单点一次被
    toggle 两次＝看起来毫无反应」，且**不报任何错**。
    **纪律**：所有 `bindXxxOnce` 首行写 `if (bindXxxOnce._done) return;
    bindXxxOnce._done = true;`（与既有 `bindAboutOnce` 写法一致）。
    读法：`alwaysReload` 管的是**数据重拉**，`Once` 管的是**事件只绑一次**。
16. **★ 合并期的"重新设计"会以设计令牌的形式悄悄留下来**（W9 补记）：
    功能对齐做了三轮，配色却一直是合并期自己定的那套
    （强调色 `#25F4EE` 而非原版 `#3ecfcf`、底色 `#0E1116` 而非 `#0f1117`）。
    用户感知到的不是「少了个功能」，而是「哪里都不对」。
    **纪律**：核对原版时，**设计令牌要和控件清单一起比**
    （原版 `app/ui/theme.py` 的 `COLORS` 就是唯一真值），
    并在 `verify_w4` 里把关键色值**逐项钉死**，防止再次漂移。
17. **★ 「有数据才显示」的容器不能装必备动作**（W9 补记）：
    「复制全部」原本放在 `#rs-url-card`（`display:none` unless 有数据）里，
    于是用户在空结果时**根本看不到复制入口**，反馈为"连复制按钮都没有"。
    **纪律**：页头动作区的按钮必须**无条件可见**；只有内容区才允许随数据显隐。
18. **★ 任务的"收尾事件"必须自带结果数据**（W10 补记）：
    `Job.finish()` / `cancel_finish()` 原来只发一句提示文字、不带 `data`，
    结果只躺在任务快照 `values` 里。前端的完成回调只从**事件**取数，
    于是「采集完成」永远显示「共 0 个账号：完成 0」—— 看起来像一条都没采到。
    **纪律**：任何"任务结束"事件都要把消费者需要的字段一起下发；
    前端也不要把「空数据」渲染成「0」，宁可提示去看明细。
19. **★ 桌面通知锚定「屏幕可用区」的右下角，且位置必须可被脚本断言**（W10 立、W11 定稿）：
    W10 曾把通知改成屏幕居中，W11 用户明确要求回到右下角 —— 但**不是**简单地
    贴屏幕边角。定稿规则：
    * 用 `SPI_GETWORKAREA` 取**可用区**（已扣任务栏；任务栏在底部/顶部/左右都算对），
      **不要**用 `screen_h - H - 64` 这种硬编码（v1.3.0 就是因为没扣任务栏、
      边距又大，看着像程序自己的角标）；
    * 锚定可用区右下角并留 **24px** 边距（`margin` 常量），多条通知沿竖直方向
      以固定 `PITCH` 向上错开；
    * 位置必须能被验收脚本断言：子进程把最终几何写进 `TK_NOTIFY_DEBUG` 指定的
      JSON（含 `x/y/w/h/screen/work/margin/slot`），脚本据此算「距右边 / 距下边」。
    **纪律**：任何"弹窗该出现在哪"的改动，都要同时给出一条可机器验证的判据。

20. **★ 窗口几何是用户资产，必须持久化**（W11 补记）：
    用户用鼠标调过一次窗口大小，就意味着他表达了一个偏好 —— 下次启动必须还原。
    实现要点（`desktop.py`）：
    * 落盘 `runtime/window_state.json`（原子写 `tmp.replace`），失败只 warning，
      **绝不能**因为存不下窗口尺寸而启动失败；
    * 最大化期间 `resized` 报的是「铺满屏幕」的尺寸 → 只记 `maximized` 标志，
      **不要把最大化尺寸当窗口尺寸写进去**；Windows 最大化/贴边会报 `-8,-8`，
      负坐标一律不记（否则下次标题栏露在屏幕外）；
    * 拖拽时事件高频触发 → 1.2s 防抖；关窗前再兜底读一次实时几何；
    * 尺寸/位置恢复前必须校验（小于最小值、大于屏幕、位置跑出屏幕 → 丢弃回落默认）。

21. **★ 原版「面板」是复合控件，还原时别只还原按钮**（W11 补记）：
    原采集器的 `LinkTextPanel` 不止两个按钮 —— 它是「模式切换 + 复制选中 +
    复制全部 + 条数显示 + 可框选的等宽文本区 + 右键菜单 + Ctrl+A/Ctrl+C」一整套。
    合并版此前只搬了「复制」和「保存为 TXT」，还把它塞进「有数据才显示」的卡片里，
    于是用户看到的就不是原来的东西。
    **纪律**：还原一个原版控件，先读它的源码把**能力清单**列出来再逐项实现；
    `audit_ui_parity.py` 的白名单只允许"确实用等价交互承载"的条目，
    一旦在合并版里原样实现了，就要把它从白名单移回硬判据。

22. **★ 「数据视图」必须每次进入都重拉，且重拉时要连「当前选中项」的内容一起刷**（W12 补记）：
    「每日归档」的文件按天整体替换，而该视图既没走 `alwaysReload`、`loadDaily()` 里
    又只在第一次进入时才 `openDaily()` —— 两个问题叠加，正文永远停在首次进入时的那一份。
    用户点「复制」拿到的自然是他上次看到的内容，而不是磁盘上最新的归档。
    **纪律**：凡是「内容会被外部流程改写」的视图（结果 / 归档 / 历史 / 日志）一律
    `alwaysReload`；刷新时列表**和当前选中项的正文**都要重拉。
    另：**复制/导出一律取服务端返回的完整原文**，不要从 DOM 的 `textContent` 取 ——
    DOM 里还有高度裁剪、滚动位置，"看得见"与"复制到"必须是两回事。

23. **★ 并列展示的标签不能塞进「会被省略号压缩」的列**（W12 补记）：
    账号行里「昵称 + @账号 + 地区标签」原本全塞在 `.acct-name`（`nowrap` + `ellipsis`）内，
    实测用户名结束位与标签起点只差 0~1px，「越南」看着就是压在账号上。
    **纪律**：会被压缩/截断的容器里**只放"允许被截断"的内容**；
    徽章、标签、状态一律作为独立的 flex 项（`flex: 0 0 auto`），
    由布局保证固定间距，而不是靠字符间距碰运气。
    验收方式：量 `tag.left - user.right` 的像素差（≥ 8px），别靠肉眼。

24. **★ 按钮是「同一套语义在生产环境里的重复实现」，一致性必须靠脚本锁住**（W12 补记）：
    全站 89 个按钮里，图标是彩色 emoji（⏸ ▶ ⏹ 🔄 🗑 📂 📁 ↺ 📥 🧹 📜 📱 ⏻ 🔍 ＋）
    与完全无图标各占一半；「暂停」在采集页是橙实心、在去水印/高清页却是透明描边；
    「复制全部」有 4 种长相（青实心 / 青实心小 / 透明 / 透明小）；
    「登录账号」还用了警告橙。**这些都不是设计选择，而是逐页各写各的产物。**
    **纪律**：
      · 图标一律走 `data-ico` + CSS `mask` 渲染的单色矢量（`background-color: currentColor`），
        这样图标自动跟随按钮文字色，紫底白、描边灰、禁用一起变暗，零外部资源零字体依赖；
        **禁止**拿彩色 emoji 当图标 —— 它自带系统配色，与设计令牌必然冲突；
      · 语义色按**操作语义**定，不按页面定（暂停 / 继续 / 停止 / 复制 / 危险 全站唯一）；
      · 危险操作不占页头首位，与普通动作之间用 `.btn-sep` 隔离；
      · 纯视图开关（全选 / 全不选 / 反选 / 今天 / 昨天）**不带**图标 ——
        判据是「会不会改数据 / 发起操作」：会则带，不会则不带。
    **验证**：`verify_w7.py [3g]` 断言 ① 按钮文案零彩色 emoji；② 每个 `[data-ico]` 的
    `::before` 计算尺寸非 0（mask 真的生效，不是写了个空类）；③ 四组跨页同色；
    ④ `#rs-clear` 不在动作区首位；⑤ `.btn-sep` 在场；⑥ 无 `float:right` 内联样式；
    ⑦ 采集页参数工具栏在默认窗口宽度下**不折行**（单行 ≈56px / 折行 ≈98px）、
    四个动作按钮同处一行且已包成 `.toolbar-actions` 一组、该行余量 ≥ 20px。
    ⚠️ **工具栏是「差几像素就折行」的高危区**（W12 把按钮统一到 34px 后，
    采集页参数行需求 1208 > 内宽 1186，只差 20px 就把「停止」顶到第二行落单）。
    给工具栏加控件/加宽按钮后，**必须实测这一行的 `clientWidth - 需求宽 ≥ 20px`**，
    并让动作按钮包成一组，这样窄窗口折行时也是整组移动而不是拆散。
    ⚠️ 两个踩过的坑：
      (a) `float` 在 flex 容器里本就被忽略 —— 页头那 3 处 `style="float:right"` 是**死代码**，
          "靠右"从来没生效过；一律改用 `.btn-push`（`margin-left: auto`）。
      (b) 给实心按钮加顶部内高光时直接写了 `rgba(255,255,255,.16)`，
          被 `verify_w4 [B2]「:root 之外零字面色值」` 当场打回 —— 一律走 `--btn-hi` 令牌。

25. **★ 共享缓存的「有没有」不能当作「我该不该初始化自己页面控件」的判据**（W12.1 补记）：
    用户报「采集任务的地区没了，只能选全部，没有越南、缅甸」。
    根因：`loadCollect()` 把「填地区下拉 / 采集日期 / 账号间隔 / 时区」**整块**
    写在了 `if (!S_.meta) { ... }` 里面。而 `S_.meta` 是**全局跨页共享**的缓存，
    侧栏里「账号管理」恰好排在「采集任务」**前面** —— 用户先去账号管理，
    `S_.meta` 就已有值，再进采集任务时整块被跳过：
    地区下拉永远只剩「全部地区」、采集日期与账号间隔是空框
    （空的账号间隔还会被 `parseFloat('') || 0` 当成 **0 写回配置**，等于取消了账号间停顿）、
    时区标签停在占位「时区 —」。
    ⚠️ **这个缺陷从 v1.0.0 就潜伏至今**（已用 v1.0.0 打包副本比对确认，非某次改动的回归），
    且**只在特定进入顺序下出现**：单独点开「采集任务」反而是好的 —— 肉眼点两下必漏。
    **纪律**：
      · 取共享缓存（`if (!S_.meta) ...`）与自己页面的控件初始化**必须解耦**；
      · 每个控件用**自己的**判据决定要不要初始化：
        下拉用 `options.length <= 1`（自愈式，填充函数幂等）、
        可编辑输入框用页面自己的 `collectInited` 标志 + `!value` **双重**守卫
        （只补空值，绝不覆盖用户已改的内容）；
      · 填充类函数一律写成**幂等**：先记住 `sel.value`，重建后能恢复就恢复、
        恢复不了才回退到首项（`fillRegionSelect` 即此形状）。
    **验证**：`verify_w7.py [3h]` 刻意按「先账号管理 → 后采集任务」的顺序进入，
    断言地区下拉完整（含越南 / 缅甸 / 各地账号数）、采集日期与账号间隔已补默认值、
    时区为真实时区，并**真的**选中「越南」筛出账号且自动勾选（7 项）。

## 七、W4 前端必须继承的 UX 契约

以下规则来自采集器旧界面（tkinter）的实测修正，属**用户明确要求的行为**，
重写为网页时必须原样保留（原测试已随 UI 撤下，改由前端验收）：

| # | 规则 | 来源 |
|---|---|---|
| 1 | 「清空链接」用**按钮内联二次确认**，不弹模态对话框（模态框被遮挡会卡住） | results_page |
| 2 | 「开始采集」**不弹确认框**：目标已在右侧"已选择"区明确展示，点击即开始 | chat_page |
| 3 | 会话/账号行**整行可点**（含名称与空白区），不是只有左侧小圆圈能点；选中行高亮 | chat_page |
| 4 | 结果表**含「采集时间」列**，并按采集时间倒序 | results_page |
| 5 | 打开程序时结果区**必须为空**（只有"本次采集完成"或主动查询才显示） | results_page |
| 6 | 默认只显示**本次采集**的结果，不是库里全部历史 | results_page |
| 7 | 账号页昵称列在账号列**之前**；昵称为空显示占位符并统计"N 条待获取" | accounts_page |
| 8 | 采集任务页切地区 = 自动勾选该地区全部，但**跨地区的已有勾选要保留** | collect_page |

## 八、已知限制

- **发布包已实测**：`scripts/package.py` 打出的 `TK素材工坊_v1.0.0.zip`
  为 **4.39 GB**（打包源 6.94 GB / 21054 个文件，压缩率 63%，耗时 257 秒）。
  包内实测：**用户数据 0 个文件混入**、随身内核 317 文件在包内、
  `docs/screenshots` 与 `scripts` 均已排除。
  `docs/` 保留文档但跳过体积较大的 `screenshots/`；`scripts/` 为开发产物不进包。
  上述三条由 `package.py` 的硬闸门自动断言。
- 程序总体积约 **8.2G**（构成：`venv` 4.9G，其中 torch 独占 4.1G；`models` 1.2G；
  `data` 1.2G 为**用户数据**，含 21 个账号的 Chromium 登录态；`tools/ffmpeg` 296M；
  `gfpgan` 186M；**`runtime/ms-playwright` 437M 随身浏览器内核**；`python-runtime` 90M）。
  如需进一步压缩，可换 CPU 版 torch 降至约 3.8G，代价是超分推理慢 5～10 倍。
- 已精简：删掉 gradio（198M，v4 已不用）、`torch/include`、全部 `__pycache__`，
  以及内核里用不到的 `chromium_headless_shell`（271M），合计较合并前少约 1.5G。
- **启动器体积 109 KB**：编译为 .NET Framework 4.8（Windows 10/11 自带），
  不引入额外的 .NET 运行时依赖。
- 采集侧的**界面已完成**（W4）：采集工作流 6 视图（采集任务 / 账号管理 / 采集结果 /
  每日归档 / 好友群聊 / 任务中心）与素材制作 5 视图 + 系统 2 视图共用同一套设计系统，
  全部走后端 `/api/collector/*` 34 条路由。
- 采集内核自带的 20 个 tkinter 界面测试未迁移（形态已变），
  改为 W4 的网页端验收 + 上面的 UX 契约表。
- **真实采集仍是替换式记录**：同一次采集会先删所选账号的既有作品再重采，
  因此调用 `/api/collector/collect` 必须显式传账号或 `all=true`；
  W5 端到端冒烟中的「真实采集 1 账号」属破坏性操作，需用户确认后执行。
- ⚠️ **替换式记录 + 任务中途取消 = 尾部账号留空缺**（2026-10-08 真实使用中发现）：
  引擎在**任务开头就把所选账号的旧记录一次性清掉**，再逐个采集。
  若用户在采完前关窗（或服务被中断），排在后面的账号会处于
  「旧记录已删、新记录未采」的空状态。当天实测：选 15 个账号 → 采完 11 个即取消
  → 4 个尾部账号（本文记为 A / B / C / D）的作品记录为空。
  **数据未丢失**（`backups/` 有当日 16:02 备份，且这 4 个账号下次采集会自然补齐），
  但用户体验上会看成「数据没了」。
  **建议改进方向**（尚未实施，涉及采集内核两条并行实现 `engine.py` /
  `collect_logic.py`，须同步修改并重跑五条铁律门禁）：把「清除旧记录」从任务开头
  下移到**每个账号开始采集时**，使单个账号的「清除 + 采集」成为一个原子单元 ——
  这样中断最多只影响正在采的那一个账号。
- **随身浏览器内核已内置**（W5-E）：`runtime/ms-playwright/`（437 MB），
  由 `collector/bootstrap.py::_use_bundled_browsers()` 在导入 playwright 之前接管。
  已通过「模拟干净机器」验证（把 `LOCALAPPDATA` 指向空目录仍可启动），
  换台电脑拷贝整个文件夹即可采集。
