## 二、根因专章：cmd 弹窗一直闪（已定位到行）

### 2.1 为什么会闪

启动器用 `pythonw.exe` 拉起 Python（`_launcher.cs:63-64` + `CreateNoWindow=true`），所以 **Python 父进程本身没有控制台**。
Windows 的规则是：**无控制台的进程创建子进程时，系统会为子进程新分配一个控制台窗口**。
注意：`capture_output=True`（管道）**并不能**阻止控制台分配 —— 只有 `CREATE_NO_WINDOW` / `DETACHED_PROCESS` 能。

### 2.2 全部 6 个闪窗点（穷举审计结果）

| # | 位置 | 命令 | 闪窗 |
|---|---|---|---|
| 1 | `core/utils.py:35-36` `run_quiet()` | 所有 ffmpeg 编码/抽帧的**共用封装** | 🔴 确定闪 |
| 2 | `core/engines/video.py:56-60` `probe_video()` | `ffprobe ...` | 🔴 确定闪（每视频 1 次） |
| 3 | `core/engines/video.py:111-113` `_pick_encoders()` | `ffmpeg -hide_banner -encoders` | 🔴 确定闪（每视频 1~2 次） |
| 4 | `core/engines/video.py:171-181` `_sharp_encode()` | 锐化编码 | 🔴 确定闪（在编码器循环内） |
| 5 | `core/engines/video.py:267-271` | 抽帧 | 🔴 确定闪（每视频 1 次） |
| 6 | `core/engines/video.py:354-367` | 合成编码 | 🔴 确定闪（在编码器循环内） |
| — | `app.py:1259-1260` / `app.py:1282-1283` | 视频转 GIF / 抽帧 | 🟢 安全（**已正确传了** `CREATE_NO_WINDOW`） |

全树穷举 `Popen / os.system / os.popen / shell=True / STARTUPINFO` **均无其他落点**；`tiktok/` 包不产生任何子进程。

### 2.3 为什么会「一直」闪

- AI 路径最好情况：`ffprobe` + `-encoders` + 抽帧 + 编码 = **4 次闪窗/视频**
- 编码器回退时（`h264_nvenc→h264_mf→libx264`）：**7 次闪窗/视频**
- 锐化路径：**3~5 次闪窗/视频**
- 再乘以批量文件数：**20 个视频 ≈ 80~140 个黑窗**

> 顺带纠正一个直觉误区：**不是每帧闪一次**。抽帧是 1 次 ffmpeg 调用，编码是 1 次（每个候选编码器一次），逐帧循环（`video.py:301-329`）是纯 torch/cv2，不产生子进程。所以「一直闪」的真凶是**每视频 3~7 次 × 批量文件数**。

### 2.4 修复（一处改动消灭 4/6 个闪窗点）

_CREATE_NO_WINDOW = getattr(subprocess, "CREATE_NO_WINDOW", 0)

def run_quiet(cmd: list, **kwargs) -> subprocess.CompletedProcess:

    kwargs.setdefault("stdin", subprocess.DEVNULL)   # 顺便解决 stdin 句柄无效

### 3.3 新进程模型

```
用户双击 TK去水印高清程序.exe（C# 启动器，仅做外壳职责）
   │  ① 单实例互斥（Mutex "Global\\TKNoWatermark"）—— 已开则激活已有窗口并退出
   │  ② 定位 Python（venv\Scripts\pythonw.exe）
   │  ③ 写运行时端口文件 runtime\server.json（动态端口）
   ▼
pythonw.exe desktop.py        ← 唯一入口（替代 app.py 直接启动）
   ├─ 后台线程：Gradio 服务绑定 127.0.0.1:<动态端口>，inbrowser=False, prevent_thread_lock=True
   ├─ 主线程：pywebview 原生窗口（WebView2），加载 http://127.0.0.1:<动态端口>
   └─ 关窗即退：demo.close() → 清理 .work 临时目录 → 释放端口 → exit
   ▼
后端依然是既有的 core/ 与 tiktok/（不动）
```

### 3.4 关键设计点

| 设计点 | 做法 | 解决什么 |
|---|---|---|
| 动态端口 | 探测 7860~7879 空闲端口；实际端口写 `runtime/server.json`；下次启动前先读并回收残留 | **消灭已发生的固定端口崩溃** |
| 单实例 | C# 命名 Mutex + Python 侧 socket 探测；重复双击 → 聚焦已有窗口 | 双开抢端口、双托盘 |
| 动态端口 + C# 等待 | C# 不再**启发式轮询 7860**，改为等待端口文件出现（避免误判/休眠误杀）；等待期只在极短窗口内运行 | 启动可靠性 |
| 优雅退出 | 关窗 → `demo.close()` → 结束子进程树；不再用 `os._exit()` 硬杀 | 端口/临时文件残留 |
| 托盘 | **C# 与 Python 二选一**（建议保留 C#，Python 侧彻底移除 `tray.py` 调用） | 双托盘 |
| 局域网模式 | 默认 `lan_access=false`；开启时**强制**生成/要求非空密码 | 零认证暴露 |
| 浏览器 | 删除 `inbrowser=True`（`app.py:2451`）与 C# 的 `TryOpenBrowser()` | 不再弹浏览器 |
| 进程树 | 启动器用 **Windows Job Object（KILL_ON_JOB_CLOSE）** 绑定 Python 子进程 | 启动器被强杀后 pythonw 变孤儿、占死端口 |
| 服务线程 | Gradio 服务必须跑在 **daemon 线程** | 否则 `threading._shutdown` 会永久 join，程序关不掉 |

### 3.5 关窗即退的正确写法（避免半截文件/残留端口）

```python
# desktop.py（示意）
import os, sys, socket, threading, time
import webview
from pathlib import Path
from core.config import PROJECT_ROOT, load
import app as core_app

def _free_port(lo=7860, hi=7879):
    for p in range(lo, hi + 1):
        with socket.socket() as s:
            if s.connect_ex(("127.0.0.1", p)) != 0:
                return p
    raise SystemExit("7860-7879 端口全部被占用，请关闭其他实例后重试")

port = _free_port()
demo = core_app.build_ui()
core_app._DEMO = demo

def serve():
    demo.queue(default_concurrency_limit=4).launch(
        inbrowser=False, prevent_thread_lock=True, quiet=True,
        server_name="127.0.0.1", server_port=port,
        allowed_paths=[str(PROJECT_ROOT)],   # 其余根目录在启动后追加（已实测生效）
    )

threading.Thread(target=serve, daemon=True, name="gradio").start()

# 等待就绪（TCP 探测），失败必须给用户可见的错误
deadline = time.time() + 60
while time.time() < deadline:
    if socket.socket().connect_ex(("127.0.0.1", port)) == 0:
        break
    time.sleep(0.2)
else:
    raise SystemExit("服务启动失败：请查看 logs 目录")

win = webview.create_window("TK去水印高清程序", f"http://127.0.0.1:{port}")

def _shutdown():
    try:
        core_app._tk_cancel.set()          # 协作式取消，别硬杀
        demo.close()                        # 释放端口
    except Exception:
        pass
    return True                             # 允许关窗

win.events.closing += _shutdown
webview.start(gui="edgechromium")           # 必须占用主线程
_shutdown()
os._exit(0)                                 # 兜底：防 GPU/worker 线程吊住进程
```

### 3.6 渲染层决策：**已确认采用方案 B —— 自研 FastAPI + HTML/JS，彻底移除 Gradio**

> 决策已定（用户确认）：不再保留 Gradio，改为自研前端。理由与代价如下，这是本方案最关键的范围变化。

| | 方案 A：保留 Gradio + pywebview | **方案 B：自研 FastAPI + HTML/JS（已选定）** |
|---|---|---|
| 原生窗口诉求 | ✅ 满足 | ✅ 满足 |
| 界面自由度 | 中（受 Gradio 组件层约束） | ✅ **完全自由**：侧边栏双板块、无刷新路由、真实进度条、空状态全可控 |
| 启动/内存 | 稍重（Gradio 依赖链 + 子进程） | ✅ 更轻更快，无 Gradio 子进程开销与版本升级风险 |
| 工作量 | 小 | **大**：需重写 UI 装配与全部回调契约 + 前端 |
| 风险 | 低 | 中高，但可用「后端契约不变 + 前端分期上线」把风险压住 |

**关键有利事实（把「大工程」变成「可控工程」）**：
- `core/` 目录 **100% 无 Gradio 依赖**（实测：`gr.*` 引用在前 1622 行只有 9 处，且 313/322 都在 `build_ui` 内）。
- 现有处理函数（`do_parse` / `_tk_download_worker` / `_hd_worker` / `handle_mixed` / `safe_*`）返回的是**普通值**（元组/字典/列表），**唯一的结构性例外**是 `app.py:732` 的一个 `gr.update(choices=...)`。
- 因此「移除 Gradio」真正的工程量在于**框架能力再实现**，而不是业务逻辑移植：
  | 必须自研的能力 | 对应现状 | 规模 |
  |---|---|---|
  | SSE/流式进度 | 5 个 generator + 0.3s 轮询状态字典（`app.py:749,1031`） | 中 |
  | 文件上传 + 临时路径映射 | 5 个 `gr.File(type="filepath")` | 中 |
  | 受控静态/结果文件服务 | `allowed_paths` + `_add_allowed_path` | 小（自研后天然可控） |
  | 控件替换 | Gallery / Dataframe / CheckboxGroup / Dropdown / Slider-as-progress | 中 |
  | 主题迁移 | `ui/theme.py` 725 行 CSS 需从 `.gradio-container` 作用域解开（`54,62,238,245-250,298-322,423` 行） | 小 |
- **推荐做法**：先建 `ui/bus.py` 抽象（`notify()` / `progress()` / `emit()`），把业务层的 9 处 `gr.*` 与状态轮询统一收口；这样前端可以**分期替换**（先替换一个板块，另一个仍走旧路径），把回归面切成小块。

## 附录 J · v4.0.0 实测反馈修复（2026-10-05 第二轮）

用户实测后报告的 3 个问题，均已定位到根因并修复。

### 问题 1：高清修复 100% 失败 —— 报错 `'Real-ESRGAN 通用轻量 x4（快速）,realesr-general-x4v3'`

**根因**：后端 `MODEL_CHOICES = [(名称, key), ...]` 是**元组列表**，而第 3 期前端把每个元组整体塞进了
`<option value>`。浏览器把数组转成字符串后，提交上来的 `model_key` 变成了
`"显示名,key"` 这种四不像，`MODELS[key]` 直接 KeyError —— 图片、视频、混合三条路径全废。

**修复（双层防护）**：
1. 后端 `/api/hd/models` 改为返回 `{value: key, label: 中文名}` 结构（新增
   `selectable_model_options()` / `selectable_scale_options()` / `selectable_side_options()`）；
2. 前端用 `value = key`、显示文本 = label；
3. **再加一层防御**：新增 `resolve_model_key()`，能把「key / 纯名称 / 显示名,key / 垃圾值」
   统一解析成合法 key，实在认不出才回退默认模型并记警告。以后前端再写错也不会整条链路崩；
4. 视频档位同样加了 `_norm_side()`（接受 `sharp` / `1920` / `"1920（推荐）"`）；
5. 文件列表为空时返回 **422 明确提示**，不再拖到 worker 里悄悄失败。

### 问题 2：高清处理完成但「结果为空」

### 问题 3：解析完成但下载不了

### 关于「解析为什么那么慢」的说明

**这是设计使然，不是 bug**：tikwm 公共 API 限流为 **1 请求/秒**，代码里按 1.15 秒/条排队
（`tikwm.py` 的 `_MIN_INTERVAL`）。所以 3 条链接**最少**要 ~4.5 秒，加上网络/代理耗时，
你看到的 ~9 秒属于正常范围。链接越多总耗时线性增长。

**能省的部分已经做了**：解析结果有本地缓存（TTL 45 分钟），
45 分钟内重复解析同样的链接会直接命中缓存、不再发请求。
如果你经常解析同一批链接，第二次会明显变快。
想再快只能减少每条链接的等待，但那会触发 tikwm 限流导致失败 —— 不建议改。

## 附录 L · v4.0.2：修复「解析完没有结果 / 不能下载」

**现象**：点「开始解析」，日志正常显示出 `✓ #1 …` `✓ #2 …` `✓ #3 …`，
但下方表格始终是「暂无数据」，下载按钮一直是**禁用状态**（鼠标移上去是禁止符号）。

### 根因（后端事件顺序错误）

解析线程里我写成了：

```python
job.finish(msg)                      # ← 先结束
job.emit(STATE, data={"items": ...}) # ← 再推结果（已经晚了）
```

`job.finish()` 会让前端的 `EventSource` **立即关闭 SSE 连接**
（前端收到 `job_done` 就 `es.close()`），所以紧跟其后的那条「带 items 的 STATE 事件」
**永远送不到前端**。后端其实解析成功了（日志里那三行 `✓` 就是证明），
但结果数据丢在了路上 —— 前端拿不到 items → 表格空白 → 没有可勾选项 → 按钮禁用。

**修复（三层）**：

1. **后端**：调整顺序为「先推结果、再 finish」（成功与异常两条路径都改了）。
2. **前端**：新增 `applyData()` 统一处理结果数据并缓存最近一次结果；
   `job_done` 时**再重放一次**，即使未来后端顺序又写错，UI 也不会空白；
   同时给结果渲染包上 try/catch，渲染异常只写日志、不再连带把按钮锁死。
3. **体验**：解析完成后**默认全选**，下载按钮立刻可点。
   并给按钮加了 `title` 提示（"请先在上面勾选要下载的项目" / "请先解析链接"），
   不让用户只看到一个禁止符号却不知道原因。

### 实测（真实 HTTP + SSE 链路复现验证）

### N.2 过程中挖出的真实 Bug：处理完成后任务被判失败

**这是本轮最有价值的发现，用户并未反馈，是我在真机验收时撞出来的。**

现象（真机复现）：所有文件都处理完了，结果画廊也显示了产物，但任务被标记为失败。

根因链条：

```
frontend/js/app.js  img_scale: $("hd-scale").value   ← 下拉框尚未被 boot() 填充时为空字符串
        ↓
server/api.py  /api/hd/start
        ↓
server/services.py  _hd_worker(... img_scale="" ...)
        ↓（所有文件处理完之后）
server/services.py:1203  _remember_choices("image", image_model, img_scale)
        ↓
server/services.py:387   sv = _scale_value(scale)
        ↓
server/services.py:319   return int(str(s).replace("x", ""))
        ↓
ValueError: invalid literal for int() with base 10: ''
```

关键危害：`_remember_choices` 只是保存「上次使用的参数」，属于锦上添花，
但它位于**所有文件处理完成之后**（`services.py:1203`），异常直接把整个任务拖成 failed，
用户辛苦跑完的产物全部不返回。触发条件很窄（例如点开始过快、参数还没填好），
所以一直没被发现。

修复（`server/services.py`）：

1. `_scale_value()` 改为容错：`None` / 空串 / 「自动」/ 无法识别的写法一律返回 `None`，
   只对能解析的返回整数。默认值仍由调用方用 `MODELS[model]["scale"]` 兜底。
2. `_remember_choices()` 整体包 `try/except`，失败只记一条 warning 日志。
   **原则：偏好保存永远不能影响任务结果。**
3. 顺带把 `int(max_side or 0)` 也做了保护（同一个函数里的同类风险）。
4. 新增模块级 `log = logging.getLogger("tk.services")`。

# 附录 O · v4.0.4：修复「双击没反应」与「关于页更新日志」

本附录记录 v4.0.4 的两个修复。它们的共同点是：**代码路径平时跑不到，
一跑到就整个功能不可用**，而且其中一个正是本项目立项时就要消灭的
「静默失败」——修完 v4.0 的端口静默退出之后，启动阶段又出现了一个新的静默退出。

## O.1 症状与定位过程

用户侧现象：**双击 `TK去水印高清程序.exe` 什么都没发生**。
没有窗口、没有托盘图标、没有错误弹窗，`app.log` 的时间戳停在上一轮运行。

对比实验把范围一路收窄：

| 实验 | 结果 |
| --- | --- |
| 直接 `pythonw.exe desktop.py`（workdir=项目根） | **第 2 秒**就生成 `runtime/server.json`，`app.log` 正常写入 → `desktop.py` 本身完全正常 |
| 启动 exe，观察 48 秒 | **不产生任何子进程，`app.log` 时间戳不变**，启动器进程却一直存活 |
| 手工模拟启动器的探测命令 | `exit=0`，**0 秒**返回 → 探测逻辑没问题 |
| 端口占用 / 残留 python 进程 / `webview` 缺失 / `pyvenv.cfg` | 全部排除 |

因为启动器是 `winexe` 且 `ShowInTaskbar=false` 且窗体已 `Hide()`，
任何弹窗都可能是「看不见的阻塞」，纯观察无法区分「卡住」和「静默退出」。

于是写了一个**独立诊断程序**（`_diag_launcher.cs`，编译成控制台 exe 后运行），
把启动器的每一步都打印出来，并且**特意只 `Process.Start` 而不重定向输出**
以复现真实调用方式。它一次就把根因打出来了：

```
4b Process.Start 异常: ArgumentException: 已添加项。
   字典中的关键字:"NO_PROXY"所添加的关键字:"no_proxy"
```

## O.2 根本原因

`_launcher.cs` 的 `StartServer()` 里有这两行（v4.0 之前就有）：

```csharp
psi.EnvironmentVariables["TK_TRAY_HOSTED"] = "1";
psi.EnvironmentVariables["TK_NATIVE"] = nativeMode ? "1" : "0";
```

.NET Framework 的 `ProcessStartInfo.EnvironmentVariables` 返回的是
**大小写不敏感的 `StringDictionary`**。本机进程环境里同时存在
`NO_PROXY` 与 `no_proxy` 两个变量（来自父进程注入的本地代理工具，
特征：值是 `172.30.213.60,192.168.0.1,.local,localhost,127.0.0.1,::1,[::1]`，
并伴随 `NODE_USE_ENV_PROXY`）。往这种字典里写第一个键时，它会先枚举
现有环境并把每一项都塞进去，于是 `NO_PROXY`/`no_proxy` 直接撞键 → 抛异常。

这个异常**极容易被误判**：连 PowerShell 自己的 `Get-ChildItem Env:`
在同一环境下都会报「已添加了具有相同键的项」。

而 `StartServer()` 是从**窗体 `Load` 事件**里调用的，**没有任何 try/catch**。
异常发生的时刻，窗体还没显示、`SetupTray()` 还没执行 →
用户看到的就是「双击没反应」。

> 关键点：`psi.EnvironmentVariables` 里的 `NO_PROXY` 与本项目毫无关系，
> 只是「往子进程环境加一个变量」这个动作触发了 .NET 对全环境的枚举。

## O.3 修复

1. **删掉那两行环境变量赋值**（根治，而不是绕过）。
   已核实全项目**没有任何代码读取** `TK_TRAY_HOSTED` / `TK_NATIVE`
   —— 只有备份目录 `_backup_v3.0.1_pre_v4.0_*/tray.py` 和 `retired_tray.py` 里有，
   它们服务于 v3 的 Python 托盘，而托盘早已由启动器自己负责。
   改为**完整继承父进程环境**（不触碰 `EnvironmentVariables`）。
2. **给整个启动流程加异常捕获**，并新增 `launcher.log`：
   - `Main()` 注册 `AppDomain.UnhandledException` + `Application.ThreadException`
     + `Application.SetUnhandledExceptionMode(CatchException)`，并 try 住 `Application.Run`。
   - `OnLoad` 拆成 `OnLoad`（try/catch 外壳）+ `OnLoadCore()`（原逻辑）。
   - 新增 `Fatal(where, ex)`：把 `ex.ToString()` 落盘到 `launcher.log` 并弹提示，
     落盘失败也不会再抛。
   - 新增 `SayError(message)`：原来两处 MessageBox 后直接 `Application.Exit()`，
     现在同时写日志。
   - `OnWatch` 的 `catch { }` 改为 `catch (Exception ex) { Fatal(...); }`，
     并且 `child.ExitCode` 先取到局部变量再用（避免取两次）。
3. 顺手删掉两处**同名死代码**（见 O.4）。

## O.6 经验记录

1. **「双击没反应」在本项目是复发型问题。** v4.0 修的是端口耗尽后的静默

2. **`.NET` 的 `ProcessStartInfo.EnvironmentVariables` 不要随便写。**
   在环境包含同名不同大小写变量的机器上（本机 `NO_PROXY`/`no_proxy`），
   任何一次赋值都会异常。要加环境变量应优先用 `psi.Environment`（Ordinal 忽略大小写、
   可覆盖），或者干脆不写、完整继承。
3. **同名函数重复定义是真会发生的。** 抽取 `app.py` → `services.py` 时
   新旧实现并存，Python 静默取后者。已把「AST 扫描重复顶层定义」
   纳入验证手段 —— 这类 bug 用肉眼读文件几乎发现不了。
4. **诊断要造对照实验，不要靠观察。** 一个 20 行的独立诊断 exe
   （把每步结果打印出来、且**只 Start 不重定向**）比反复猜启动器卡在哪快得多。
5. **持久化位置决定危害等级。** v4.0.3 的「跑完却判失败」之所以严重，是因为
   出错代码位于**所有处理完成之后**；本次 `changelog_markdown` 只影响一个展示页，
   危害低得多 —— 判断 bug 优先级要先看它在流程里的位置。
